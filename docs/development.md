国歌クイズの仕様と、開発・運用の詳細をまとめた文書。**仕様の正本はこの文書**で、外から見る人向けの概要は [README](../README.md) にある。

**Phase 1〜3 が完了。**データ検証と出題エンジン（UI非依存）、テスト、GitHub Actions による CI、クイズの画面、
36か国の音源（米海軍軍楽隊の演奏が中心）、main へのマージで自動公開（Cloudflare Workers）までを実装済み。
PC と iOS の Safari・Chrome で、一通り遊べることを確認している。

## セットアップ

必要なもの：Node.js 24（LTS。バージョンは [.node-version](../.node-version) に書いてある）、pnpm 10。

```bash
# pnpm が未インストールの場合（どちらか一方）
corepack enable pnpm     # Node 同梱の Corepack を使う（管理者権限が必要な場合あり）
npm install -g pnpm@10   # npm でグローバルに入れる

pnpm install
```

`package.json` の `packageManager` で pnpm のバージョンを固定している。

## ディレクトリ構成

```text
data/
  anthems/<id>.json        本番用の国データ（1国1ファイル。現在は36か国）
  melody-groups.json       同一・類似旋律グループ（収録していない国も参照できる）
  countries.json           世界の国の一覧（地域・知名度の分類。誤答と超級の候補にも使う。収録していない国も含む）
public/
  audio/<id>.mp3           音源（権利を確認したものだけ。ビルド時にそのまま配信される）
scripts/
  validate-data.ts         pnpm validate:data の本体
  lib/read-data-dir.ts     Node(fs) でデータを読み込む（スクリプトとテストで共有）
src/
  lib/schema/              Zod スキーマと、z.infer で導出した型
  lib/data/validate.ts     検証の本体（スキーマ＋横断整合性）。読み込み方法に依存しない
  lib/data/bundled.ts      Vite の import.meta.glob で本番データを自動収集
  lib/countries/           超級の入力候補の検索（表記の揺れをそろえて比べる）
  lib/random/              シード付き乱数（mulberry32）とシャッフル
  lib/quiz/                出題エンジン（条件フィルター・旋律クラス・クリップ・セッション生成）
  lib/game/                画面の状態遷移（モード選択 → プレイ中 → 結果）の reducer
  lib/audio/               音源の URL を作る（配信元の切り替えとパス走査の防止）
  components/              画面の部品（モード選択・クイズ・音声プレーヤー・結果・出典一覧）
  App.tsx, main.tsx        画面の切り替えと起動
  styles.css               スタイル（ダークモード対応）
tests/
  fixtures/anthems/        テスト用の架空国の国歌データ（18件）
  fixtures/countries.json  テスト用の架空国の一覧（収録していない架空国8件を含む26件）
  fixtures/melody-groups.json
  fixtures/invalid/        わざと壊したJSON（検証エラーのテスト用）
  helpers.ts               fixture 読み込み・架空国の生成・セッションの不変条件チェック
  *.test.ts
```

**分け方の理由**：出題ロジックと検証ロジックは React・Vite・Node のどれにも依存しない純粋な TypeScript にし、
ファイルの読み込みだけを環境ごとに分けた（Vite は `bundled.ts`、Node は `read-data-dir.ts`）。
こうするとアプリと `validate:data` で同じ検証を使え、テストもブラウザなしで高速に実行できる。

## 国データの追加手順

1. **音源を選び、権利を確認する**（下の「音源の選び方」）。
2. 音源を `public/audio/<id>.mp3` に置く。
3. `data/anthems/<id>.json` を1つ作る（`<id>` は ISO 3166-1 alpha-2 の小文字。例：`jp.json`）。
   `audio.durationSec` には音源の実際の長さ（秒）を書く。
4. `data/countries.json` のその国の項目を確かめる。国名が国歌データと同じか（違うと `validate:data` がエラーになる）、
   地域（`region`）と、初級に入れるか（`famous`）が適切か。
5. 聴き分けられない国・似ている国があれば `data/melody-groups.json` にグループを追加する。
6. `pnpm validate:data` と `pnpm test` を実行する。長さが0.5秒より大きくずれていると、`validate:data` がエラーで知らせる。

国データの一覧ファイルの編集やコードの変更は不要（`import.meta.glob` で自動的に読み込まれる）。

### 音源の選び方

- 米海軍軍楽隊（United States Navy Band）の演奏を、[Wikimedia Commons](https://commons.wikimedia.org/) から使う。
- ファイルのページの「Licensing」で、次の2つがそろっていることを人が確認する。
  - **Performance（演奏）**：米海軍の職務上の著作物としてパブリックドメイン（`PD-USGov-Military-Navy` など）。出典が米海軍軍楽隊（navyband.navy.mil）の記録であること。
  - **Composition（楽曲）**：楽曲自体もパブリックドメイン（作曲者の没年が十分に古い、など）。最近作られた国歌は楽曲の著作権が残っていることがあるので注意する。
    **米国でもパブリックドメインである根拠**（`PD/1923`・`PD-old-auto-1923` のように「米国で保護が切れる年より前に出版」を示す表示。2026年の時点では「1931年より前」で、毎年1年ずつ進む）があることを確かめる。
    「更新されなかった」「著作権表示がなかった」といった根拠（`PD-US-not renewed`・`PD-US-no notice` など）だけのものは、確かめにくいので採用しない。
    作曲者の没年による表示（`PD-old-100`・`PD-old-70` など）しかないページは、米国での根拠が示されていない。
    その場合は、1931年より前に出版されたことを別の記録（出版された楽譜など）で確かめ、その出典を `license.note` に書く（例：オーストラリア）。確かめられなければ収録しない。
    原産国で保護期間が切れているだけ（`PD-old-auto` だけ）では足りない。1996年の時点で原産国で保護されていた外国の作品は、米国で権利が回復している場合がある（URAA）。
- ページの**冒頭に削除依頼（Deletion request）などの警告が出ていない**ことを確かめる。Licensing の欄だけを見ると見落としやすい。
- 楽曲とは別に、**録音に使われた編曲**の権利が問題になることがある（作曲者ではなく、編曲者の没年で保護期間が決まる）。
- 元のファイルは Ogg 形式が多いが、Safari でも再生できるように、Commons が用意している **MP3 の変換版**（ファイルページの「Transcode status」や API の `derivatives`）を使う。
- `license` には、出典として Commons のファイルページの URL を書き、`note` に楽曲と演奏それぞれのパブリックドメインの根拠を書く。
- 米国政府の著作物がパブリックドメインなのは「米国では」とされている。他の国での扱いは厳密には国ごとに異なるが、このプロジェクトでは許容できるリスクと判断している。
  日本から公開するうえでは、楽曲はどれも作曲者の没後70年を過ぎている。一方、米海軍軍楽隊の録音（2003年ごろ）に日本の著作隣接権が及ぶかどうかは確認しきれていない。
  米海軍軍楽隊が公開用に配布している録音であることを踏まえて、これも同じく許容できるリスクとしている。
- **米海軍軍楽隊以外の音源**は、ライセンスと出所をはっきり確認できたものだけを使う（例：中国は、Commons の利用者が楽譜から自作した演奏で、CC BY-SA 3.0）。
  `license.type` にライセンスの種類、`author` に作者、`note` にライセンスの正式名称と URL・変更点（MP3 への変換など）を書く。出典の一覧に表示される。
  音色がほかの国の録音と大きく違うと、音色だけで答えが分かってしまうので、収録する前に聴いて確かめる。

```json
{
  "id": "jp",
  "nameJa": "日本",
  "nameEn": "Japan",
  "anthemTitle": { "original": "君が代", "ja": "君が代" },
  "audio": { "file": "jp.mp3", "durationSec": 62.5 },
  "composer": "（任意）",
  "adoptedYear": 1999,
  "license": {
    "type": "public-domain",
    "author": "（演奏者・録音者）",
    "sourceUrl": "https://（実際の出典URL）"
  }
}
```

### 項目と命名規則

- `id`：小文字2文字。ファイル名は必ず `<id>.json`。
- `nameJa`・`nameEn`：`countries.json` の同じ国と同じにする（出典の一覧に表示する）。
- 地域と難易度の分類は、国歌データには書かない（`countries.json` で管理する）。
- `audio.file`：ディレクトリを含まないファイル名（拡張子込み、`.mp3` か `.ogg`）。英小文字・数字・`.` `_` `-` のみ使え、`..` は禁止。
- 定義されていない項目（タイプミスなど）はエラーになる。

### 国の一覧（`countries.json`）

```json
{
  "id": "jp",
  "nameJa": "日本",
  "nameEn": "Japan",
  "region": "asia",
  "famous": true,
  "aliases": ["にほん", "にっぽん"]
}
```

- 国連加盟国193か国と、バチカン・パレスチナ・コソボ・台湾の計197。国歌を収録していない国も含む。
  4択・8択の誤答と、超級の入力候補に使う（収録している国だけを使うと、選択肢や候補から答えを絞り込めてしまうため）。
- `region`：`asia` / `europe` / `africa` / `north-america` / `south-america` / `oceania`。
  - 国連の地理区分（M49）に従う。中東・中央アジア・コーカサス・トルコはアジア、中米・カリブは北アメリカ。
    例外として、キプロスはヨーロッパにする（EU 加盟国で、国歌がギリシャと同じ）。
  - クイズで選ぶ地域は、これをまとめたもの（下の「出題ルール」）。「全世界」はクイズ条件の特別値なので、ここには書かない。
- `famous`：その地域の中で比較的知名度が高い国だけ `true` を書く（初級の対象）。書かない国は中級の対象。
  `false` は書かない（検証でエラーになる）。全世界の初級は、各地域の初級を合わせたもの。
  分類を見直すときは、この値を書き換えるだけでよい。
- `aliases`：別名・読み（「米国」「USA」「にほん」など）。超級の候補を探すときに使う。
  別の国の名前・別名と（表記の揺れを除いて）同じになってはいけない（候補で区別できなくなるため。検証でエラーになる）。

### 旋律グループ（`melody-groups.json`）

```json
[
  {
    "id": "god-save-the-king",
    "relationType": "identical",
    "countryIds": ["gb", "li"],
    "description": "リヒテンシュタイン国歌は、イギリス国歌と同じ旋律"
  }
]
```

- `identical`：聴き分けられない。同じ選択肢には並べず、超級ではどちらを答えても正解にする。A=B かつ B=C なら A=C とみなす。
- `similar`：似ているが聴き分けられる。上級で誤答として優先する。直接同じグループにいる組だけが対象。
- グループが参照する国は `countries.json` にある必要がある。国歌を収録していない国も参照できる
  （例：フィンランドとエストニア。エストニアを収録していなくても、フィンランドが正解の問題でエストニアを誤答に並べないため）。

### ダミーデータと本番データの区別

- テスト用の架空国は `tests/fixtures/` にだけ置き、ISO でどの国にも割り当てられない
  ID（`aa`、`qm`〜`qz`、`xa`〜`xz`、`zz`）を使う。`xk` はコソボで事実上使われているので予約IDから外している。
- 本番データの検証では、予約IDと `example.com` などのダミーURLをエラーにする。
  fixture を誤って `data/` にコピーしても、`validate:data` が失敗する。
- **Zod の検証に通っても、法的に利用できることの確認にはならない。** 出典と許諾は人が確認する。

## データ検証の仕組み

| 層            | 内容                                                                                                                                | 状態     |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------- | -------- |
| 1. スキーマ   | 型・必須項目・ID形式・ライセンス・音源ファイル名                                                                                    | 実装済み |
| 2. 横断整合性 | ID重複、ファイル名とIDの一致、音源ファイル名の重複、国の一覧との照合、旋律グループの参照先・重複・メンバー数、本番への fixture 混入 | 実装済み |
| 3. 音源       | 音源ファイルがあるか、読み取れるか、実際の長さと `durationSec` の差が0.5秒以内か。使われていない音源の警告                          | 実装済み |

国の一覧（`countries.json`）も第1・2層で検証する：形式、ID の重複、本番での予約ID、
別の国と（表記の揺れを除いて）同じ名前・別名がないか、収録しているすべての国が一覧にあり、国名が国歌データと同じか。
アプリの起動時にも同じ検証（第1・2層）を行う。

第3層は Node だけで動く（[scripts/lib/check-audio.ts](../scripts/lib/check-audio.ts)）。音源の長さは `music-metadata` で読み取る。
本番データが0件のとき、`pnpm validate:data` は `[WARN]` を表示して終了コード 0 で終わる。
データがあるときは、地域ごとの収録国の数（初級／中級）と、各モードの出題可能数を一覧表示する。

## 出題ルール

- 地域：国の6地域を、次の4つ（＋全世界）にまとめて出題する。対応は [src/lib/quiz/modes.ts](../src/lib/quiz/modes.ts) の `QUIZ_REGIONS` だけで決まる。

  | クイズの地域       | 国の地域（`region`）             |
  | ------------------ | -------------------------------- |
  | 全世界             | すべて                           |
  | アジア・オセアニア | `asia`・`oceania`                |
  | ヨーロッパ         | `europe`                         |
  | アメリカ           | `north-america`・`south-america` |
  | アフリカ           | `africa`                         |

  2026年11月に、地域ごとの収録数の偏りを減らすため、6地域から変更した。

- 難易度ごとの出題範囲と答え方（設定は [src/lib/quiz/config.ts](../src/lib/quiz/config.ts) の `answerPool`・`answerFormat`・`choiceCount`）：

  | 難易度 | 正解にする国（選んだ地域の収録国） | 答え方                                         |
  | ------ | ---------------------------------- | ---------------------------------------------- |
  | 初級   | `famous` の国                      | 4択                                            |
  | 中級   | `famous` でない国                  | 4択                                            |
  | 上級   | すべて                             | 8択                                            |
  | 超級   | すべて                             | 記述式（国名を入力し、表示される候補から選ぶ） |

  初級と中級は重ならない。2026年11月に、それまでの「初級・中級・上級が知名度の3段階、超級がすべて」から変更した。

- 正解は、選んだ地域・難易度に合う**収録国**からだけ選ぶ。
- 誤答は、選んだ地域の**すべての国**（`countries.json`。収録していない国を含む）から選ぶ。ほかの地域の国では補わない。次の順に優先する：
  1. 上級：正解と `similar` の関係にある国
  2. 初級・中級：正解と同じ分類（`famous` か、そうでないか）の国。分類が違う国が混ざると、
     「初級の正解は有名な国」と分かっているので、聴かなくても消去法で答えが分かってしまうため
  3. 残りの国

  同じ順位の中は乱数で選ぶ。収録国を優先はしない（未収録の国も、同じ分類なら同じように選ぶ）。

- 選択肢のどの2か国も、同じ `identical` クラスに属さない（収録していない国も含めて判定する）。
  地域の国のクラス数が選択肢の数（4・8）に足りなければ、そのモードは0問になる。

- 記述式（超級）：
  - 選択肢を作らない（`choiceIds` は空）。条件に合う収録国が1か国あれば出題できる。同じ旋律の国が同じプレイで出題されることもある。
  - 正解として認める国（`acceptedIds`）は、正解国と同じ `identical` クラスに属する**すべての国**（地域・収録の有無によらない）。
    同じ旋律の国は音だけでは区別できないため。選択式では `acceptedIds` は正解国だけ。
  - 答えは `countries.json` の国（世界の197か国）から選ばせる。地域を選んでいても、候補は世界の国すべて。
    自由な文字列は受け付けないので、表記の揺れで不正解になることはない。
  - 候補の探し方（[src/lib/countries/index.ts](../src/lib/countries/index.ts)）：国名・英語名・別名を、ひらがな/カタカナ、全角/半角、大文字/小文字、
    アクセント記号、空白・中黒などの違いを無視して比べる。完全一致 → 前方一致 → 途中で一致 の順に最大8件を出す。
- モードを作りかけのときは、設定（[src/lib/quiz/config.ts](../src/lib/quiz/config.ts)）で `available: false` にすると、
  出題可能数は0、`generateSession` は `MODE_UNAVAILABLE` を返し、モード選択の表には「準備中」と表示する（現在、該当するモードはない）。

- 1プレイは最大10問。成立する問題が10問未満ならその数だけ出し、0問なら開始できない（`INSUFFICIENT_POOL`）。
- 正解国は1プレイ内で重複しない（誤答としての再登場は許可）。
- 再生区間（暫定）：**全難易度で冒頭から60秒**。イントロで最初の数秒に何も流れない音源があり得るため。
  音源が60秒より短ければ、音源全体を再生する。難易度による違いは、出題対象の国と答え方（上級の誤答の選び方、超級の記述式）だけになる。
  設定は [src/lib/quiz/config.ts](../src/lib/quiz/config.ts) にまとめてある。途中から再生する機能（`start: "random"`）は残してあり、設定を変えるだけで使える。
- 乱数は引数で渡す（`rng`）。同じデータ・条件・シードなら同じ問題列になる。入力データの並び順にも左右されない。

```ts
import { generateSession } from "./src/lib/quiz";
import { mulberry32 } from "./src/lib/random";

// data は { anthems, countries, melodyGroups }（検証済みのデータ）
const result = generateSession(data, {
  region: "europe",
  difficulty: 2,
  rng: mulberry32(42), // 本番では Math.random を渡してよい
});
if (result.ok) console.log(`1 / ${result.totalQuestions}`);
```

出題可能数の表示には `countAvailableQuestions` を使う。`generateSession` と同じ判定なので、表示される問題数と実際の問題数は必ず一致する。

## 画面の動き

- **モード選択**：地域 × 難易度の20通りを表で示し、それぞれの問題数を表示する。出題できない組み合わせ（収録国がない）は「—」で、選ぶと理由を表示し、スタートできない。
- **プレイ中**：「問題 1 / 7」のように進み具合を示す。地域・難易度・問題列は開始時に固定され、途中では変えられない。
  - 音声は**自動再生しない**。「再生」を押すと出題区間（冒頭から最大60秒）を流す。ブラウザが再生を拒否したとき（`NotAllowedError`）と、読み込みに失敗したときは、それぞれ案内を表示する。
  - 選択肢（初級・中級は4つ、上級は8つ）から1つ選ぶと、正解・不正解と、正解の国名・曲名を表示する。1問に答えられるのは1回だけ。
    8択は狭い画面でも2列で並べ、ボタンを少し低くする。
  - 超級では、国名を入力すると候補が出る。候補をクリック（タップ）するか、上下キーで選んで Enter で答える（日本語入力の変換中の Enter は無視する）。
    答えた後は、自分の回答と正解を表示し、同じ旋律の国があればそれも正解だったことを示す。
  - 「終了」を押すと、「進行状況は破棄されます」と確認してからモード選択に戻る。
  - プレイ中にページを閉じる・再読み込みしようとすると、ブラウザの確認を出す。**進行状況は保存しない**（再読み込みすると最初から）。
- **結果**：正答数と各問題の正誤を表示し、「同じモードでもう一度」か「モード選択へ戻る」を選べる。
- **出典**：画面の下に、音源の出典とライセンスの一覧を、国データから自動で表示する。

状態遷移のルールは [src/lib/game/index.ts](../src/lib/game/index.ts) の reducer にまとめ、React の部品からは切り離している（テストは `tests/game.test.ts`）。

## テスト

`pnpm test` で実行する。主な内容：

- **データ検証**（`data-validation.test.ts`）：正しいデータは受理し、不正な fixture と多数の形式違反を拒否する。
  横断整合性のエラーの検出（国の一覧との照合、収録していない国を参照する旋律グループを含む）、fixture が本番データに混入していないことも確認する。
- **旋律・乱数・クリップ**（`melody-random-clip.test.ts`）：`identical` の推移閉包、`similar` が推移しないこと、
  乱数の再現性、再生区間が音源内に収まること（短い音源も含む）。
- **セッション生成**（`session.test.ts`）：20モードすべて × 30シードで不変条件を検査する。
  さらに、地域のまとめ方、代表的なモードの出題数、初級と中級が重ならないこと、誤答の選び方（未収録の国を使う、
  初級・中級は同じ分類を優先し足りなければ補う、同じ旋律の国を並べない、ほかの地域へ広げない）、上級の8択と類似優先、
  超級（記述式）で同じ旋律の国（未収録を含む）を正解にすること、境界条件（0・1・3・4・10・11か国、同一旋律ばかり、8択に必要なクラス数）、
  `maxQuestions` の扱い、決定性を確認する。
- **画面の状態遷移・音源の URL**（`game.test.ts`）：開始後に条件が変わらないこと、1問1回答、未回答で進めないこと、
  途中終了・再挑戦、`generateSession` の問題列で最後まで遊べること、記述式の回答と正誤判定、不正な音源ファイル名を拒否すること。
- **国の一覧と入力候補**（`countries.test.ts`）：表記の揺れのそろえ方、候補の並び順と件数、別名での検索、
  `countries.json` の検証（本番データが通ること、どの地域にも初級の国があること、形式違反・ID の重複・区別できない名前・本番での予約IDを報告すること）。
- 画面そのもの（ボタンの操作や音声の再生）のテストは、Phase 4 で Playwright を使って行う。
  そのときに、音声の読み込みに失敗した後、通信が戻ってから「もう一度試す」で再生できること（Phase 3 のレビューで見つかった不具合）も回帰テストにする。

fixture はおおまかな仕様の確認に使い、件数の境界条件はテスト内で架空国を必要な数だけ作って確認している（`makeData`）。
こうすると、境界ごとに fixture ファイルを増やさずに済む。

## CI（GitHub Actions）

[.github/workflows/ci.yml](../.github/workflows/ci.yml) で、PR の作成・更新時と main への push 時に次を順に実行する。
どれか1つでも失敗すると CI 全体が失敗になる。

`pnpm install --frozen-lockfile` → `lint` → `format:check` → `typecheck` → `validate:data` → `test` → `build`

- `--frozen-lockfile`：`pnpm-lock.yaml` と `package.json` が食い違っていたら失敗させる（手元と同じ依存関係で検証するため）。
- 権限は `contents: read` だけにしている。
- 使うアクションはタグではなくコミット SHA で固定している。タグは後から別のコミットに付け替えられるため。
- Node のバージョンは `.node-version` で一元管理し、CI もこのファイルを読む（`node-version-file`）。Node を上げるときは、このファイルと `package.json` の `engines`・`@types/node` を一緒に変更する。
- main は Rulesets で保護している。直接の push・force push・削除は禁止で、`check` ジョブが成功した PR だけをマージできる。

### 依存関係の自動更新（Dependabot）

[.github/dependabot.yml](../.github/dependabot.yml) で、毎週月曜に npm パッケージと GitHub Actions の更新 PR を作らせる。

- minor・patch の更新は1つの PR にまとめる。CI が通れば、内容を確認してマージする。
- 公開されてから7日未満の版は提案させない（`cooldown`）。乗っ取られたパッケージをすぐ取り込まないため。
- メジャー更新は、原則としてパッケージごとに別の PR になる。問題が起きたときに原因を切り分けやすくするため。
- ただし、**互いの版に依存していて同時に上げないと成り立たないもの**は、メジャー更新を1つの PR にまとめる。
  - Vite 系（`vite`・`@vitejs/*`・`vitest`）：`@vitejs/plugin-react` 6 は Vite 8 が必須。
  - ESLint 系（`eslint`・`@eslint/*`・`eslint-plugin-*`・`typescript-eslint`・`globals`）：`@eslint/js` 10 は ESLint 10 が必須。
  - 別々にしていたときは、どちらも単独では上げられず、週次の更新処理全体が「Dependabot cannot update to the required version」で失敗した（2026年11月）。
- `@types/node` はメジャー更新を提案させない。型定義を、実際に使う Node のメジャー版（`.node-version`）に合わせるため。
- `typescript` のメジャー更新も、`typescript-eslint` が TypeScript 7 に対応するまで提案させない。
- minimatch（ESLint 経由）の脆弱性の警告は、ESLint 側が修正版に対応するまで「Dependabot cannot update minimatch to a non-vulnerable version」と出続けるが、想定どおり。
- 脆弱性の修正（セキュリティ更新）はこの設定とは別の仕組みなので、メジャー更新でも PR が作られる。

## 公開（CD）

main にマージされると、[.github/workflows/deploy.yml](../.github/workflows/deploy.yml) が **Cloudflare Workers の静的アセット**として `dist/` を公開する。
設定は [wrangler.jsonc](../wrangler.jsonc) にあり、Worker のスクリプトは使わず、ビルドした静的ファイルだけを配信する。

- 流れ：`pnpm install --frozen-lockfile` → `validate:data` → `test` → `build` → `wrangler deploy`。
  main の内容は PR の CI で検証済みだが、公開の直前にもう一度確かめる。
- Cloudflare の API トークン（`CLOUDFLARE_API_TOKEN`）とアカウント ID（`CLOUDFLARE_ACCOUNT_ID`）は、GitHub の **`production` 環境のシークレット**に置く。
  `production` 環境は main ブランチからしか使えない設定にして、PR のワークフローからはトークンを読めないようにする。
- API トークンの権限は「Edit Cloudflare Workers」だけにし、対象は自分のアカウント1つに絞る。
- wrangler は `package.json` で版を固定し、外部のアクション（`cloudflare/wrangler-action`）は使わない。版の管理を `pnpm-lock.yaml` と Dependabot にまとめるため。
- 公開は1つずつ順番に行い、途中で取り消さない（`concurrency`）。Actions の画面から手動でやり直すこともできる（`workflow_dispatch`）。
- 手元で設定を確かめるときは、`pnpm build` の後に `pnpm exec wrangler deploy --dry-run` を実行する（ログイン不要。実際にはアップロードしない）。
- 設計書では Cloudflare Pages を予定していたが、Cloudflare が新しいプロジェクトには Workers の静的アセットを勧めているため、こちらにした。

## 開発の進め方（AI エージェントとの分担）

| ファイル                                                                | 内容                                                             |
| ----------------------------------------------------------------------- | ---------------------------------------------------------------- |
| [AGENTS.md](../AGENTS.md)                                               | すべての AI エージェントが守る共通のルール（Codex は自動で読む） |
| [CLAUDE.md](../CLAUDE.md)                                               | Claude Code（実装担当）固有の進め方。AGENTS.md を読み込む        |
| [REVIEW.md](../REVIEW.md)                                               | リスクに応じたレビューの観点と、AI にレビューを頼む手順          |
| [.github/pull_request_template.md](../.github/pull_request_template.md) | PR の本文の形式（検証結果と AI レビューの記録）                  |

| 担当                         | 役割                                   |
| ---------------------------- | -------------------------------------- |
| Claude Code                  | 実装・テスト・文書の更新               |
| Antigravity CLI（Gemini）    | push 前の事前レビュー（手元）          |
| Codex                        | GitHub 上の PR レビュー                |
| GitHub Actions（CI `check`） | 自動テストと品質ゲート（マージの条件） |

どの AI レビューをいつ使うかは、変更のリスクに応じて [REVIEW.md](../REVIEW.md) で決めている。AI のレビューは助言で、マージの必須条件は CI の `check` だけ。

**PR の確認**：`pnpm pr:status [PR番号]` で、CI・Codex のレビュー・指摘・手元とのずれをまとめて表示する（読み取りだけ）。
Claude Code では `/pr-check [PR番号]` で、この結果をもとに指摘の確認と「採用／不採用／要相談」の判断、マージしてよいかの判断まで行う（[.claude/skills/pr-check/SKILL.md](../.claude/skills/pr-check/SKILL.md)）。
最後に、PR の本文の「## AI レビュー」の表を `pnpm pr:ai-review <PR番号> <ファイル>` で埋める。書き換えるのはこの節だけで、本文の他の部分は変えない。

この書き換えには GitHub CLI（`gh`）を使う。`gh` には、**このリポジトリの Pull requests の読み書きだけ**を許可した Fine-grained personal access token（有効期限つき）を登録しておく。
コードの変更・マージ・設定の変更ができるトークンは使わない。

**マージ後の後片付け**：`pnpm sync` で、手元を最新の状態にする（`--dry-run` を付けると、何をするかの表示だけ行う）。

1. main に切り替えて、GitHub の最新を取り込む（早送りだけ）。
2. `pnpm install --frozen-lockfile` を実行して、依存関係を main に合わせる（毎回実行する。そろっていればすぐ終わる）。失敗したら、ブランチを削除する前に止まる。
3. 手元のブランチのうち、**先頭のコミットが、マージ済みの PR の先頭のコミットと一致するもの**だけを削除する。
   push していないコミットがあるブランチや、まだ PR がマージされていないブランチは残し、理由を表示する。

コミットしていない変更があるときや、手元の main に GitHub にないコミットがあるときは、何もせずに止まる。GitHub 側は変更しない。

## 技術選定の理由

- **Vite + React + TypeScript（strict）**：静的サイトの標準的な構成。`noUncheckedIndexedAccess` も有効にし、配列の範囲外アクセスを型で見つけやすくしている。
- **Zod 4**：JSON の実行時検証と TypeScript の型を1か所で定義できる（`z.infer`）。
- **Vitest**：Vite と設定を共有でき、TypeScript をそのまま実行できる。
- **music-metadata**：`validate:data` の第3層で、音源の実際の長さを読み取るために使う（開発時のみ。サイトには含まれない）。
- **tsx**：`validate:data` の実行に使う。Node 24 は型を取り除くだけなら TypeScript を直接実行できるが、import に拡張子を書かない今のコードの書き方には対応していないため。
- **ESLint + Prettier**：Lint と整形を分けて担当させる標準的な組み合わせ。
- **wrangler**：Cloudflare への公開に使う（開発時のみ）。手元で Worker を動かす部品（`workerd`）のインストール時スクリプトは実行させていない（公開には不要なため）。

## 未決事項（Phase 1 で仮に決めたものを含む）

1. **`maxQuestions` が範囲外の場合**：10 に丸めずに `RangeError` で拒否する（1〜10 の整数のみ許可）。
   出題不足（`INSUFFICIENT_POOL`）は利用者に見せる結果なので戻り値で返し、引数の誤りはプログラムの誤りなので例外にした。
2. **出題できるかどうかの性質**：誤答は同じ条件の国から選ぶので、「その条件に同一旋律クラスが4つ以上あるか」だけで決まる。
   そのため出題できる国は「条件に合う全員」か「0件」のどちらかになる。将来、誤答の選び方を変えた場合は見直す。
3. **抽選の偏り**：誤答は国単位で一様に抽選しているので、国の多い同一旋律クラスはわずかに選ばれやすい。重み付き抽選と合わせて検討する。
4. **音源ファイル名の重複**：2か国が同じ音源ファイルを指すとエラーにしている（同じ曲でも録音は国ごとに持つ前提）。
5. **`identical` と `similar` の両方に入っている組**：検証ではエラーにせず、`identical`（同じ選択肢に並べない）を優先する。
6. **再生区間**：当面は全難易度で冒頭から60秒。難易度ごとに短くするか、イントロを飛ばす開始位置（`playableRanges` など）を国データに持たせるかは、音源を揃えてから判断する。
   途中から再生する場合の開始位置は、0.01秒単位に切り捨てている。
7. **音源**：米海軍軍楽隊の演奏（Wikimedia Commons の MP3 変換版）を採用した。最初の8か国は、楽曲が十分に古い国から選んだ（イギリス・フランス・ドイツ・イタリア・オランダ・日本・インド・アメリカ合衆国）。
   中国とタイは候補にしたが、権利を確認しきれないため収録を見送った（Codex のレビューで判明）。中国の録音は、使われている吹奏楽への編曲の著作権を理由に Commons で削除依頼が出ている（2026年9月）。
   タイは、楽曲が米国でパブリックドメインである根拠がない（URAA により米国では2027年末まで保護される可能性がある）。
   2026年11月に14か国を追加した（フィリピン・マレーシア・イスラエル・バングラデシュ・アルゼンチン・ブラジル・コロンビア・ペルー・ニュージーランド・オーストラリア・ミクロネシア連邦・カナダ・メキシコ・キューバ）。
   Commons の「米海軍軍楽隊が演奏した国歌」のカテゴリ（263件）から、上の「音源の選び方」の基準を満たすものを選び、1件ずつページを確認した。
   フィジーは1970年の編曲の権利がはっきりしないため、インドネシアは広く使われている管弦楽編曲が1950年のものであるため、見送った。
   同じ月に、さらに14か国を追加して36か国にした（ポルトガル・オーストリア・ギリシャ・ノルウェー・フィンランド・スイス・デンマーク・ベルギー・チェコ・チリ・ウルグアイ・エクアドル・ボリビア・中国）。
   ポルトガル・デンマーク・チリ・ウルグアイは、出典ページに米国での根拠の表示がなかったので、出版の記録などを確認して `license.note` に書いた。
   中国は、米海軍軍楽隊の録音（編曲の権利を理由に削除依頼が出ている）ではなく、Commons の利用者が自作した演奏（CC BY-SA 3.0）を採用した。
   ルクセンブルクは、1931年より前に楽譜が出版された記録を見つけられなかったため見送った（1864年に初演、作曲者は1898年没。記録が見つかれば収録できる）。
   ベネズエラは、現在の公式版が1947年の Juan Bautista Plaza（1965年没）による改訂で、録音がどの版に基づくか確かめられず、出典ページにも米国での根拠がないため見送った。
   タイは、楽曲の米国での保護が切れる2028年以降に再検討する（別の録音に替えても、楽曲の問題は変わらない）。
   オセアニアは3か国なので、オセアニアのモードはまだ遊べない。アフリカは収録国がない。
   各国の難易度は仮の値で、国が増えてから見直す。米国政府の著作物の米国外での扱いは、上の「音源の選び方」のとおり許容できるリスクとしている。
8. **データが0件の `validate:data`**：警告を出して成功で終わる。公開前に「0件なら失敗」にするオプションを追加するか検討する。
9. 設計書の第14章に挙げた項目（難易度の付け方、旋律判定の厳密さ、対象国の定義、得点方式、状態保存、音源の配信と権利、CI/CDの権限）。
